# ADR-0002 长期迁移决策

日期：2026-09-12  
状态：已接受

## 背景

旧插件包含多个 SQLite 文件、Jinja 页面和大量历史命令。必须先建立可回滚边界，再逐步替换实现。

## 选项

保留现有运行时并包一层、合并数据库、引入前端框架、立即删除旧入口。

## 决策

- 多数据库在本轮不合并；`DatabaseCatalog` 声明所有权，跨库动作使用 operation ledger/outbox 和对账。
- 前端继续 Jinja + 原生 ES modules；公共请求、状态和 DOM 工具放在 `adapters/web/static/core`。
- 旧命令和旧 Web URL 保留一个完整发布周期，通过兼容清单、DeprecationWarning 和命中计数观测。
- 新 API 固定使用 `/api/v1`，响应携带 `request_id`；旧 URL 采用 308 转发。
- operation ledger 和审计记录至少保留到对应数据库备份过期，并在对账完成后由运维策略归档；本插件不自动删除流水。
- 远端部署采用“备份 -> dry-run 迁移 -> 隔离旧实例 -> 启动 -> 健康检查 -> 可回滚写操作”的停机窗口。

## 代价与风险

迁移期会同时存在旧注册器和新清单，必须避免同一稳定 ID 被新调度器再次执行；旧入口命中计数归零后才能删除 shim。

## 迁移和回滚

关闭新 manifest 或 feature 开关，停止写入并备份数据库与流水，恢复旧代码，运行兼容迁移，再通过 `/health/ready` 和只读命令验收。

## 影响的 feature / 数据 / API

影响全部旧玩法兼容包、`game_db` 的公共治理表、`/api/v1` 新接口以及管理端配置、任务、备份和对账页面。
