# QQ Markdown 语法与消息投递约定

本页依据用户提供的 QQ Markdown 语法示例整理，作为本仓库开发与审查的公共参考。
原示例的嵌套列表缩进已规范，重复公式已合并，收藏页脚已移除；支持的语法没有删减。
本页是随仓库维护的开发文档，不是本地 goal 或临时推进记录。

## 使用原则

- 下列语法按用户提供的支持清单使用。不得凭印象判定表格、代码块、公式或其他列出的语法不支持，并据此放弃实现。
- 文字中出现 Markdown 标记不等于消息按 Markdown 投递。必须检查实际发送链路是否构造 Markdown 消息段，最终请求是否携带 Markdown 内容或正确模板参数。
- 普通消息不负责渲染 Markdown 或行内蓝字；键盘按钮与 Markdown 内容也须通过相应消息能力发送。
- QQ 普通群、全量群消息事件、私聊和频道分别沿用项目已有的事件归一化与能力判断，不根据事件名称猜测语法支持情况。
- OneBot 复用同一业务结果，按已有实现提供可读文本或图片呈现；它的展示差异不能用来证明 QQ 不支持某种语法。
- 出现异常先核对呈现器、消息段、适配器、配置与平台返回码，修复链路后再判断语法问题。不得用宽泛异常捕获长期隐藏 Markdown 发送故障。
- 必要的普通文本回退保留，并记录回退原因；回退成功不能记作 Markdown 验收通过。真实 QQ 客户端效果未验证时如实标注待验证，不写成“不支持”。

## 标题与文本样式

````markdown
# 一级标题
## 二级标题
### 三级标题
#### 四级标题
##### 五级标题
###### 六级标题

**加粗文本**
__下划线加粗__
_斜体文本_
*星号斜体*
***加粗斜体***
~~删除线文本~~
````

标题语法属于支持范围。文字游戏的普通结果、列表和帮助通常用 `**短标题**`，避免大字号标题挤占消息空间；这是排版选择，不是能力限制。
引用适合次要提示或补充说明，不应把全部正文统一加上 `>`。
可以按语义使用 emoji，例如 ✅、⏳、❌，避免每行堆叠装饰。

## 链接与图片

````markdown
地址：<https://qun.qq.com>
[链接](https://qun.qq.com)
````

图片示例保留用户提供的 URL 与尺寸写法，不代表本次已验证该资源仍可访问。
实际产品图片使用项目的媒体上传、地址解析与发送工具，不为套用示例硬编码这个地址。

## 有序列表与无序列表

嵌套内容缩进到所属列表项的正文起始列。下面的缩进已规范，不沿用原示例不一致的两空格缩进。

````markdown
1. 第一项
2. 第二项
   - 嵌套无序列表
   - 继续嵌套
3. 第三项

- 列表项一
- 列表项二
  - 嵌套有序列表
    1. 二级列表
    2. 继续列表
- 列表项三
````

## 引用与分割线

````markdown
> 青青子衿，悠悠我心，但为君故，沉吟至今
> 四月维夏，六月徂暑。先祖匪人，胡宁忍予

----

分割线，三个及以上 -。

***

星号分割线。
````

分割线前后保留空行，避免与相邻文本组成其他 Markdown 结构。

## 表格

````markdown
| 列1 | 列2 | 列3 |
| --- | --- | --- |
| 行1 | 单元格1 | 单元格2 |
| 行2 | 单元格3 | 单元格4 |
````

表格在支持清单中。日历、属性对比等结构可以使用表格，不得因未经验证的“不支持表格”判断而退回空格拼列。
日历保留周一到周日七列，明确已签、今日和未签状态，并显示本月累计与连续天数；按实际月份生成，不能写死示例日期。
检查消息宽度与真实手机显示；需要等宽布局时，也可使用下面列出的代码块，并核对当前发送路径是否原样保留它。

## 代码块

````markdown
```python
print("Hello, World!")
```
````

代码块中的内容不再嵌套加粗或行内蓝字。蓝字、说明与操作按钮放在代码块外。

## 数学公式

````markdown
$$
E=mc^2
$$
````

公式属于支持清单；仅在内容需要时使用，不为了使用语法给普通奖励说明增加复杂度。

## 交互文本与键盘按钮

````markdown
[交互文本](mqqapi://aio/inlinecmd?command=%E4%BA%A4%E4%BA%92%E6%96%87%E6%9C%AC%E6%95%B0%E6%8D%AE&enter=false&reply=false)
[引用交互文本](mqqapi://aio/inlinecmd?command=%E5%BC%95%E7%94%A8%E4%BA%A4%E4%BA%92%E6%96%87%E6%9C%AC%E6%95%B0%E6%8D%AE&enter=false&reply=true)
````

- 行内蓝字必须位于实际 Markdown 内容中；放进普通消息或代码块不能当作已完成交互。
- 用项目现有 helper 生成链接并对完整命令正确 URL 编码，不手工拼接未经转义的用户输入。
- 文案不固定显示 `/`；实际发送或预填的命令前缀遵循宿主配置。
- 完整动作优先放少量情境按钮，名称、详情、待填参数等适合用行内蓝字；同一动作不在正文、页脚和按钮重复堆叠。
- 帮助按功能分类，子帮助中的命令可以使用蓝字，不给每个子帮助追加整片按钮网格。
- 键盘按钮通过现有适配器的 keyboard 能力发送，不把按钮配置当作 Markdown 文本语法。

## 开发验证

1. 从实际指令 handler 追踪到呈现器、消息网关和适配器请求，确认 Markdown 内容没有被转成普通 text。
2. 检查优化器、清洗器、换行处理和模板参数是否破坏表格、代码围栏、链接或公式；只对有证据的转换缺陷修复，不预先删除支持语法。
3. 用隔离 fake/capture 验证 QQ 群、私聊的最终 Markdown 消息段和 OneBot 的可读回退；业务结算共用，不重复整套业务长测试。
4. 定向覆盖 Markdown 发送失败与回退原因、命令去重及签到重放，避免为了验证呈现重复发奖励或写真实玩家存档。
5. mock、OneBot 与消息结构检查只能证明各自边界；QQ 真机呈现另记实际验证结果。不能把未验证写成不支持，也不能冒充已实测。

本页只规定支持语法与呈现验证方法，不添加部署、长时间审计或全量回归门槛。
